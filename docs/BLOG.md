# Блог Avior — «Советы мастера»

Модуль находится в **Панель → Инструменты → Блог Avior**, также в верхнем меню «Инструменты». Доступ к редактору — владелец и администратор; управление ключом ИИ — только владелец. Ветка `feature/avior-blog`. Установлено 23.09.2026 на cms.avior.moscow и avior.moscow после согласования. Все три стартовые статьи остаются черновиками.

## Работа редактора

Создайте статью, заполните текст, URL, категорию, автора, связанную услугу, SEO-заголовок и описание. Сохранение меняет только черновик. «Предпросмотр» показывает сохранённую версию после входа в CRM. При публикации создаётся отдельный снимок: последующие правки черновика не меняют сайт до повторной публикации.

Текст использует Markdown: `##`/`###` для разделов, списки, **выделение**, ссылки, цитаты-подсказки. Сырой HTML экранируется. Изображения выбираются из медиатеки; пример: `![Описание](media:КОД) "Подпись"`. Поддерживаются JPEG/PNG/WebP до 8 МБ и 20 Мп; сервер перекодирует в WebP 480/960/1600, удаляя метаданные. SVG не принимается. Неиспользуемые изображения можно удалить; связанные с черновиками, публикациями или расписанием защищены от удаления.

Дата в будущем сохраняет снимок для планировщика. Снятие публикации удаляет HTML статьи и её записи из поиска и sitemap. Смена URL удаляет прежний путь: автоматического редиректа нет, поэтому после индексации URL лучше сохранять. Редакционные замечания необходимо выполнить и очистить перед публикацией. Три стартовые статьи импортируются только как черновики и требуют проверки мастером.

## Включение на сервере после согласования

1. Сделать резервную копию БД и сайта. Применить `sql/migrations/2026_09_22_blog.sql` к существующей MySQL БД CRM. Миграция добавляет только `blog_posts` и `blog_media`.
2. Установить файлы модуля и `blog-assets/` сайта. Скопировать `config/blog.example.php` в игнорируемый `config/blog.php`, включить `enabled`, указать настоящий `site_root`, `site_url` и закрытый `private_dir` **вне обоих web-root**.
3. Требуются PHP 8.1+, PDO MySQL, mbstring, fileinfo, GD с WebP и DOM. Пользователь PHP/cron должен иметь запись в private_dir, корень сайта (для замены blog и sitemap). Запретить выдачу dot-файлов/каталогов веб-сервером. Не давать запись в конфигурацию CRM.
4. Убедиться, что есть корректный корневой `sitemap.xml`. Выполнить `php ops/blog_seed.php`, затем `php ops/blog_build.php`. Импорт идемпотентен по URL и ничего не публикует.
5. Настроить у того же пользователя cron: `* * * * * /usr/bin/php /PATH/TO/CRM/ops/blog_publish.php`. Расписание использует Europe/Moscow. На рабочем сервере установлен `/etc/cron.d/avior-blog`, запускающий `/var/www/cms/ops/blog_publish.php` от www-data.

Папка `/blog/` принадлежит генератору (маркер `.avior-blog-generated`). Посторонняя папка без маркера не перезаписывается. Генератор сначала готовит новый набор файлов, затем меняет каталог и sitemap под файловой блокировкой; при ошибке замены sitemap возвращает прежний каталог. БД и файловая система не образуют единую транзакцию: после аварийного завершения между заменой файлов и commit следует повторить `php ops/blog_build.php`. Это восстановит сайт из зафиксированных снимков БД.

`Avior-site/deploy.sh` сохраняет серверные `/blog/` и `/sitemap.xml` при rsync, чтобы очередной деплой дизайна не стёр публикации. После изменений шапки/подвала выполнить `ops/blog_build.php`. Новые публичные HTML-страницы автоматически обнаруживаются в течение минуты тем же cron, даже когда отложенных публикаций нет. GitHub Pages не является местом работы редактора: генератор должен видеть реальный каталог сайта на сервере.

## API для ассистента

Существующий `/api/ai/summary.php` остаётся read-only и не меняется. Новый `/api/ai/blog.php` использует **другой ключ**, только для чтения статей и сохранения черновиков. Нет доступа к заказам, клиентам, финансам, публикации, расписанию или удалению. Cookie-вход не заменяет Bearer. В URL ключи не принимаются. На рабочем сервере использовать только HTTPS.

Владелец открывает «Блог Avior → Доступ ИИ к черновикам», создаёт ключ и сохраняет его в защищённой конфигурации подключения ассистента. Значение показывается один раз; БД хранит SHA-256. Замена/отзыв сразу прекращают работу старого ключа. Не хранить ключ в репозитории, статьях, ссылках или открытых сообщениях. Создание интерфейса не включает доступ автоматически; рабочий ключ этой разработкой не создавался.

Запросы передают `Authorization: Bearer <ключ>`:

- `GET /api/ai/blog.php` — последние 100 статей, категории, услуги, поля и права.
- `GET /api/ai/blog.php?id=123` — сохранённый черновик и `version`.
- `POST /api/ai/blog.php`, `Content-Type: application/json` — создать/обновить черновик. Ограничение тела 256 КиБ. Для изменения передать целые `id` и текущую `version`; конфликт возвращает 409. Для создания опустить id/version. Повторное создание с тем же slug вернёт 409; следует прочитать существующую статью и обновить её по версии.

Поля: `slug`, `title`, `category`, `tags` (строка через запятую), `excerpt`, `body` (Markdown), `cover` (`media:код` или разрешённое изображение сайта, например `/cooling-photo.webp`), `cover_alt`, `cover_caption`, `author`, `seo_title`, `seo_description`, `service`, `editor_notes`. Неизвестные поля запрещены. Если замечания пустые, API добавляет требование редакционной проверки. Успех возвращает id/version и пути редактора/предпросмотра. API не загружает изображения: используйте уже добавленную в CRM медиатеку или имеющиеся иллюстрации сайта.

Рабочий сценарий: пользователь даёт тему → ассистент уточняет факты и пишет материал → сохраняет черновик → пользователь просматривает и правит → владелец/администратор публикует через CRM. Автоматической генерации по таймеру или подписки на сторонний ИИ-сервис нет.

## Проверки и ограничения

Локально проверены PHP 8.4 и отдельная SQLite-копия: публикация/снятие, неизменность live при сохранении черновика, смена URL, поиск, пагинация, sitemap, экранирование, CSRF, роли, закрытые изображения, загрузка и удаление, Bearer API и отзыв доступа. Проверено срабатывание отложенной публикации. Перед установкой миграция, публикация и снятие проверены на отдельной MariaDB-базе и закрытой копии сайта на сервере. Сборка рабочей версии выполнена от www-data.

Создать отдельный стенд: `php tests/setup_blog_preview.php /PATH/TO/Avior-site /NEW/PREVIEW`. Скрипт не читает production config. Его логин/пароль записываются в локальный `login.txt`. Запускать PHP-сервер только на `127.0.0.1:4177`, docroot `<preview>/crm/public`.

Тесты: `php tests/blog_test.php <preview>`, `python tests/blog_http_test.py <preview>`, `python tests/blog_api_test.py <preview>`. Последним нужен локальный PHP-сервер. API-тест временно включает отдельный тестовый ключ и затем отзывает его. Не запускать эти тесты на рабочей БД.

## Автоматический sitemap — 23.09.2026

`src/site_sitemap.php` собирает канонические публичные HTML-страницы, включая разделы, категории и пагинацию. `blog_publish.php` обновляет sitemap каждый минутный запуск, даже без запланированных статей. Публикация и снятие используют тот же сборщик сразу, причём до замены файлов учитывается новая версия блога. Карта обновляется атомарно только при изменении списка. Удалённые страницы исчезают. robots.txt уже ссылается на sitemap; его действующие правила сохранены и общие Allow/Disallow учитываются. Страницы с noindex, чужим canonical, технические демо, файлы проверки поисковиков, скрытые каталоги и симлинки исключены. Маршруты, создаваемые только динамически PHP, потребуют отдельного источника URL; текущий публичный сайт статический. Проверено 8 сценариев sitemap и 22 сценария редактора, а также текущая карта на сервере.
