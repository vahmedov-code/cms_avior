# АВИОР CRM — состояние проекта (читать в начале каждой новой сессии)

Этот файл — единая точка входа для продолжения проекта в новой сессии
(своей или чужой). В начале новой сессии: прочитать этот файл целиком,
затем при необходимости — код в репозитории.

Обновлять этот файл в конце **каждой** сессии, где менялся код, схема
БД или инфраструктура. Не хранить сюда пароли/токены — только факты
о проекте (см. раздел «Секреты» — они сохраняются отдельно, вне git).

---

## 1. Кто и что

- Владелец: Вейс, сервис по ремонту ноутбуков/смартфонов/планшетов
  «АВИОР», Москва, Можайское шоссе 4к1, тел. +7 901 222-81-11.
- Цель проекта: собственная CRM/CRM, постепенно заменяющая ЛайвСклад —
  учёт ремонтов, клиентов, финансов, аналитики; интеграция со своим
  сайтом; в перспективе — склад, SMS-рассылки, роли доступа.
- **Долгосрочная цель (заявлена 17.08)**: в перспективе продавать эту
  CRM как white-label другим сервисным центрам. Практическое следствие —
  избегать хардкода специфичного для АВИОР там, где легко сделать
  настраиваемым (см. `settings.php` в §5 — реквизиты компании/site_url/
  SMS теперь редактируются через интерфейс, а не зашиты в файлах).
- Стек: PHP 7.4+/8.x без фреймворка (PDO, процедурный стиль) + MySQL/
  MariaDB. Без сборки, без composer — просто файлы + document root на
  `public/`.

  pull` на сервере), но с обязательным шагом сборки после. Точный путь
  проекта на сервере (`/var/www/ux` или другой) — пока не подтверждён,
  узнать при первой реальной работе с этим сайтом.

  на квитанции — см. §5).
- БД: MySQL, база `avior_cms`, пользователь `avior_user` (пароль — только
  в `config/config.php` на сервере, туда никто, кроме Вейса, не заходит).
- **Важное правило доступа**: у ассистента (Claude) нет прямого SSH/БД
  доступа к серверу. Ассистент готовит точные команды, Вейс сам выполняет
  их по SSH. Никогда не делать вид, что команда выполнена на сервере —
  bash-песочница ассистента это его собственная изолированная среда, не
  сервер Вейса.

### Как ассистент пушит в GitHub (стандартный паттерн)

Папка `outputs/` в песочнице не даёт удалять/переименовывать файлы,
поэтому git-операции всегда через `/tmp`:

```bash
rm -rf /tmp/cms-avior-git
TOKEN="<токен>"
git clone -q "https://x-access-token:${TOKEN}@github.com/vahmedov-code/cms_avior.git" /tmp/cms-avior-git
cd /tmp/cms-avior-git
git config user.name "Avior CRM Bot"
git config user.email "cms-bot@avior.local"
rsync -a --exclude='.git' /sessions/.../outputs/cms-avior/ /tmp/cms-avior-git/
git add -A
git status --porcelain   # проверить, что нет ничего лишнего/секретного
git commit -q -m "..."
git push origin main
cd / && rm -rf /tmp/cms-avior-git
```

Всегда клонировать существующую историю (не `git init` заново) — иначе
push будет отклонён как non-fast-forward.

### Как Вейс обновляет сервер после пуша

```bash
cd /var/www/cms
git pull
# если в sql/migrations/ появился новый файл — применить его:
mysql -u avior_user -p avior_cms < sql/migrations/<новый_файл>.sql
```

Если `git pull` ругается на "dubious ownership" — разово:
`git config --global --add safe.directory /var/www/cms`.

## 3. Проверка кода (в песочнице нет PHP-интерпретатора)

Перед каждым пушем — статическая проверка:
1. Python-скрипт на баланс скобок `(){}[]`, извлекающий только код
   внутри `<?php ... ?>` (важно игнорировать HTML/CSS вне тегов —
   иначе ложные срабатывания на `{}` в инлайн `<style>`).
2. Проверка, что все `require __DIR__ . '/...'` пути существуют
   (резолвить как `dirname(path) + rel`, не через `os.path.join`,
   иначе абсолютные на вид пути ломают резолвинг).
3. Для CSS — `css` npm-пакет (`node -e "require('css').parse(...)"`).
4. При правках `account_memo_new.php`/подобных standalone print-страниц
   — вручную проверять баланс `if(...): ... endif;` в альтернативном
   синтаксисе.

## 4. Схема БД — текущее состояние

Таблицы: `users`, `clients` (+`source` ENUM), `repairs` (+`order_type`
ENUM: repair/pc_build/account_memo; +поля квитанции — см. ниже),
`repair_parts` (+`cost` для расчёта прибыли), `parts_catalog`,
`repair_status_log`, `sms_log`, `expenses`.

`repairs.order_type` — дискриминатор, который объединяет ремонты,
сборки ПК и памятки по аккаунту в один список «Заказы».

## 5. Модули — статус

Готово и в проде (с оговоркой про миграции выше):
- Авторизация (bcrypt, сессии), `setup.php` — одноразовое создание админа.
- Клиенты (+ источник: авито/яндекс/2гис/google карты/сарафан/с улицы).
- Заказы (общий список, 3 способа создания — см. ниже), статусы,
  история статусов, **SMS — три поддерживаемых провайдера** (`src/sms.php`),
  выбираются и настраиваются через **Настройки** (`settings.php`, §5 ниже) —
  без правки файлов на сервере:
  1. **SMS.ru** — дешёвая схема без своего имени отправителя (от 25 коп/SMS,
     от 7 коп при расходе >5000₽/мес). **На практике оказалось, что для
     аккаунта Вейса это НЕ работает без одобренного буквенного имени** —
     SMS.ru прямо отказывается слать («Для работы с нашим сервисом
     необходимо создать буквенного отправителя»). Имя «Avior» подано на
     регистрацию 17.08, статус «На рассмотрении», срок — 5-7 рабочих
     дней. Как только одобрят — заработает без каких-либо изменений кода.
  2. **SMSC.ru** — заглушка, интеграция не реализована (есть закомментированный
     пример в коде, как у SMS.ru).
  3. **Android-шлюз** (`android_gateway`, добавлено 17.08 как альтернатива,
     пока ждём SMS.ru) — приложение [SMS Gateway for Android](https://github.com/capcom6/android-sms-gateway)
     (open-source), облачный режим: свой Android-телефон с **обязательной**
     SIM-картой отправляет SMS через собственную сотовую сеть — клиент
     видит настоящий номер сервиса, без модерации и абонплаты. Телефону
     нужен только интернет (Wi-Fi/мобильные данные, SIM НЕ обязательно
     должна поддерживать мобильный интернет — команда идёт через
     `api.sms-gate.app`, который сам держит соединение с телефоном, обходя
     CGNAT у операторов — проброс портов не нужен). Настройка на телефоне:
     включить «Cloud Server» → «Online» → логин/пароль оттуда — в
     Настройки CRM. Вейс планирует использовать для этого телефон
     сервиса (Google Pixel 9 XL, номер +7 901 222-81-11).
  Общий для всех трёх: без выбранного провайдера — как раньше, логирует
  в `sms_log` со статусом `not_configured`, ничего не отправляет. Шаблон
  текста по умолчанию (`default_sms_message()` в `functions.php`): для
  статуса «готов» — «Здравствуйте! Вас приветствует сервис АВИОР.
  Устройство готово. С вас NNN ₽.» (сумма — комплектующие+услуги минус
  уже внесённая предоплата); для статуса «принят» — «Здравствуйте! Вас
  приветствует сервис АВИОР. Заказ NN принят в работу. Статус можно
  отследить здесь: <ссылка>» — ссылка на `order_status.php` (та же, что
  зашита в QR-код на квитанции), не на голый `avior.moscow` — виджет
  статуса туда ещё не встроен (см. бэклог), а `order_status.php` реально
  работает на `cms.avior.moscow`; для остальных статусов — прежний
  нейтральный текст «Заказ NN: статус — ...». Сотрудник видит готовый
  текст в форме и может отредактировать перед отправкой.
  **Важный урок (баг, исправлен 17.08)**: у SMS.ru верхнеуровневый
  `"status":"OK"` в ответе означает только, что сам запрос выполнен
  (авторизация/отправитель в порядке) — НЕ что конкретное сообщение
  реально отправлено. Настоящий статус — в `sms.<номер>.status`. Первая
  версия кода проверяла только верхний уровень — CRM писала «отправлено»,
  даже когда SMS.ru молча отклонял конкретный номер. Если будете
  добавлять новых провайдеров — проверяйте вложенный/per-recipient статус,
  а не только общий код ответа. **Ещё один похожий баг (исправлен 17.08)**:
  подпись под формой «SMS клиенту» была статичным текстом «провайдер не
  подключён», без реальной проверки — показывалась всегда, даже когда
  провайдер уже настроен и SMS реально уходят. Теперь `sms_active_provider()`
  в `functions.php` (та же логика приоритета БД→config.php, что в
  `send_sms()`) проверяет по-настоящему: если провайдер задан — показывает
  зелёным «SMS отправится через: <название>» (`sms_provider_label()`),
  если нет — прежнее предупреждение, но ссылкой на `settings.php`, а не
  на `config/config.php`.
- **Шаблон-просьба об отзыве** (Яндекс Карты, добавлено 18.08) — кнопка
  «📝 Попросить отзыв (Яндекс Карты)» над полем текста в форме «SMS
  клиенту» (`repair_view.php`), подставляет готовый текст с ссылкой из
  настройки `yandex_reviews_url` (`settings.php`, раздел «Ссылка на
  отзыв»). **Сознательно НЕ автоматически** — по прямой просьбе Вейса:
  сотрудник сам решает, кому и когда отправить (обычно — через несколько
  дней после выдачи заказа, вручную открывая нужный заказ). Функция
  `review_request_sms_message()` в `functions.php`, отдельно от
  `default_sms_message()` (которая привязана к статусу и работает
  автоматически при смене статуса) — этот шаблон не завязан на статус
  вообще, просто кнопка поверх текстового поля, тот же паттерн
  экранирования onclick, что и в `render_device_type_picker()`.
- **Переключатель вида списка заказов** (`repairs.php`, кнопки «▤ Плитки»/
  «☰ Список» над таблицей, видны только на мобильном ≤720px — на десктопе
  таблица и так уже табличная, переключать нечего). «Плитки» — прежнее
  поведение (каждый заказ отдельным стековым блоком с подписями полей).
  «Список» — компактная настоящая таблица со скроллом вбок (класс
  `.list-view` на `#ordersTableCard`, переопределяет мобильный CSS
  внутри `@media(max-width:720px)`). Переключение — `setOrdersView()` в
  `src/layout_footer.php` (общий файл, но действует только если на
  странице есть `#ordersTableCard` — остальные таблицы сайта, клиенты/
  сотрудники и т.д., не затронуты). Выбор запоминается в `localStorage`
  (`avior-orders-view`), применяется автоматически при следующих заходах.
- **Сортировка по клику на заголовок столбца** (`repairs.php`, по образцу
  LiveSklad — подсмотрели у них 18.08) — № заказа/Клиент/Статус/Сумма/
  Обновлён кликабельны, повторный клик переключает направление (стрелка
  ↑/↓ рядом с активным столбцом). Whitelist `$sortColumns` в коде
  (никогда не подставляется `$_GET` напрямую в `ORDER BY`). Ссылки
  сохраняют текущие фильтры (статус/тип/поиск) — `sort_link()`. Без
  явной сортировки — прежнее поведение (`ORDER BY r.created_at DESC`).
  Сортировка по «Статус» — алфавитная по значению ENUM, не по бизнес-
  порядку стадий (принят→готов→...) — если понадобится порядок по
  стадиям, нужен отдельный `CASE WHEN` или числовой столбец с весом
  статуса.
- Сборка ПК (`pc_build_new.php`) — создаёт заказ `order_type=pc_build`.
- Памятка по аккаунту (`account_memo_new.php`) — Apple ID/Google.
  **Пароли, секретные вопросы, 2FA-код НЕ сохраняются в БД** — только
  на распечатанном листе сразу после заполнения (сознательное решение
  по безопасности, Вейс уведомлён).
- Квитанция о приёмке (`repair_receipt.php`) — печать в 2 экземплярах
  (клиенту/сервису), 6 пунктов гарантийных условий по шаблону Вейса.
  В отличие от памятки — данные (серийный номер, комплектация, внешний
  вид, предоплата, срок, примечание, ФИО мастера) **сохраняются** в
  `repairs`, можно распечатать повторно без повторного ввода.
  Ставка ответственного хранения (₽/сутки) оставлена пустой строкой
  для заполнения от руки — как в оригинальном шаблоне.
  Стиль печатной формы переверстан под образец из реального экспорта
  ЛайвСклад (`Заказы.pdf`, загружен Вейсом): чёрный текст на белом,
  Arial/Helvetica, поля списком «жирная подпись: значение» без таблиц
  и цветных акцентов.
  На каждой квитанции — QR-код (через api.qrserver.com, `<img>`,
  без сервисной зависимости), ссылающийся на публичную страницу
  `public/order_status.php?order_no=...&phone=...` с текущим статусом
  заказа. При наведении на QR в браузере — тултip с текущим статусом

  давно существует, широко используется, поддерживает АТОЛ и другие ФР)

  `User`, пароль пустой. **Лицензия (уточнено 18.08)**: условно
  бесплатно — без лицензии работает ограниченное время (для тестов),
  дальше выдаёт ошибку «нет лицензии». Бессрочная лицензия — ~2000-3000₽
  разово, привязывается к **ИНН организации**, покрывает **все ККТ на
  этот ИНН** сразу (не по одной кассе). Техподдержка отдельно — первый
  год бесплатно, дальше 2000₽/год, необязательна. План: сначала
  проверить интеграцию бесплатно (пробный период), купить лицензию
  только после подтверждения, что всё работает. **KkmServer, похоже, умеет и банковский
  терминал** (у LiveSklad есть отдельная статья именно про настройку
  KkmServer для терминала Сбербанка) — велика вероятность, что одна
  программа закроет обе задачи разом, а не две отдельные интеграции.
  **Нерешённый нюанс**: CRM на HTTPS (`cms.avior.moscow`), KkmServer на
  `http://localhost` — браузеры блокируют такой запрос (mixed content).
  LiveSklad решает браузерным расширением-мостом (свой плагин
  KkmServeraddin для Chrome/Yandex/Edge, транслирует запросы со страницы
  в localhost). Альтернатива — HTTPS-порт KkmServer (5894, самоподписанный
  сертификат на 'localhost', нужно один раз принять в браузере
  сотрудника) — проще, но требует проверки, действительно ли этого
  достаточно против современных ограничений браузеров (Private Network
  Access в Chrome может потребовать доп. подтверждения даже для HTTPS→
  localhost). Решить это до начала кодирования. Ждём модель терминала
  эквайринга и проверку, поддерживает ли его KkmServer напрямую (список
  поддерживаемых терминалов есть у LiveSklad/kkmserver.ru) — если да,
  одна интеграция вместо двух, если нет — вопрос терминала решаем
  отдельно после подтверждения модели.

## 7. Как продолжить в новой сессии

1. Прочитать этот файл.
2. Если папка `outputs/cms-avior/` уже на месте (сохраняется между
   сессиями) — работать с ней напрямую.
3. Если папки нет (новая среда/новый компьютер) — клонировать репозиторий
   заново по ссылке из §2 (нужен свежий токен от Вейса, если старый не
   сохранён/отозван).
4. Перед пушем — прогнать проверки из §3.
5. После значимых изменений — обновить этот файл (модули/миграции/бэклог)
   и запушить вместе с кодом.
