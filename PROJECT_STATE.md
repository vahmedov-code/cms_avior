# АВИОР CMS — состояние проекта (читать в начале каждой новой сессии)

Этот файл — единая точка входа для продолжения проекта в новой сессии
(своей или чужой). В начале новой сессии: прочитать этот файл целиком,
затем при необходимости — код в репозитории.

Обновлять этот файл в конце **каждой** сессии, где менялся код, схема
БД или инфраструктура. Не хранить сюда пароли/токены — только факты
о проекте (см. раздел «Секреты» — они сохраняются отдельно, вне git).

---

## 1. Кто и что

- Владелец: Вейс, сервис по ремонту ноутбуков/смартфонов/планшетов
  «АВИОР», Москва, Можайское шоссе 4к1, тел. +7 901 222-81-11.
- Цель проекта: собственная CMS/CRM, постепенно заменяющая ЛайвСклад —
  учёт ремонтов, клиентов, финансов, аналитики; интеграция со своим
  сайтом; в перспективе — склад, SMS-рассылки, роли доступа.
- Стек: PHP 7.4+/8.x без фреймворка (PDO, процедурный стиль) + MySQL/
  MariaDB. Без сборки, без composer — просто файлы + document root на
  `public/`.

## 2. Репозиторий и инфраструктура

- GitHub: `https://github.com/vahmedov-code/cms_avior.git`, ветка `main`.
- Токен доступа (Personal Access Token) — **не хранится в этом файле и
  не коммитится в git**. Хранится отдельно (см. раздел «Секреты» ниже).
  Если токен утрачен/отозван — попросить у Вейса новый.
- Сервер: Ubuntu 26.04, Nginx + PHP-FPM 8.5. На сервере уже живут другие
  сайты (`avior.moscow`, `shop.avior.moscow`, `ux-src`) — **их нельзя
  задевать** при любых изменениях nginx-конфигов.
- CMS развёрнута в `/var/www/cms` (document root — `/var/www/cms/public`).
  Домен **`cms.avior.moscow`** — реальный, рабочий, подтверждён Вейсом,
  не изменится. SSL выпущен и подтверждён Вейсом вручную. Использовать
  этот домен как окончательный везде, где нужен публичный адрес CMS
  (например `site_url` в `config/config.php` для QR-кода статуса заказа
  на квитанции — см. §5).
- БД: MySQL, база `avior_cms`, пользователь `avior_user` (пароль — только
  в `config/config.php` на сервере, туда никто, кроме Вейса, не заходит).
- **Важное правило доступа**: у ассистента (Claude) нет прямого SSH/БД
  доступа к серверу. Ассистент готовит точные команды, Вейс сам выполняет
  их по SSH. Никогда не делать вид, что команда выполнена на сервере —
  bash-песочница ассистента это его собственная изолированная среда, не
  сервер Вейса.

### Как ассистент пушит в GitHub (стандартный паттерн)

Папка `outputs/` в песочнице не даёт удалять/переименовывать файлы,
поэтому git-операции всегда через `/tmp`:

```bash
rm -rf /tmp/cms-avior-git
TOKEN="<токен>"
git clone -q "https://x-access-token:${TOKEN}@github.com/vahmedov-code/cms_avior.git" /tmp/cms-avior-git
cd /tmp/cms-avior-git
git config user.name "Avior CMS Bot"
git config user.email "cms-bot@avior.local"
rsync -a --exclude='.git' /sessions/.../outputs/cms-avior/ /tmp/cms-avior-git/
git add -A
git status --porcelain   # проверить, что нет ничего лишнего/секретного
git commit -q -m "..."
git push origin main
cd / && rm -rf /tmp/cms-avior-git
```

Всегда клонировать существующую историю (не `git init` заново) — иначе
push будет отклонён как non-fast-forward.

### Как Вейс обновляет сервер после пуша

```bash
cd /var/www/cms
git pull
# если в sql/migrations/ появился новый файл — применить его:
mysql -u avior_user -p avior_cms < sql/migrations/<новый_файл>.sql
```

Если `git pull` ругается на "dubious ownership" — разово:
`git config --global --add safe.directory /var/www/cms`.

## 3. Проверка кода (в песочнице нет PHP-интерпретатора)

Перед каждым пушем — статическая проверка:
1. Python-скрипт на баланс скобок `(){}[]`, извлекающий только код
   внутри `<?php ... ?>` (важно игнорировать HTML/CSS вне тегов —
   иначе ложные срабатывания на `{}` в инлайн `<style>`).
2. Проверка, что все `require __DIR__ . '/...'` пути существуют
   (резолвить как `dirname(path) + rel`, не через `os.path.join`,
   иначе абсолютные на вид пути ломают резолвинг).
3. Для CSS — `css` npm-пакет (`node -e "require('css').parse(...)"`).
4. При правках `account_memo_new.php`/подобных standalone print-страниц
   — вручную проверять баланс `if(...): ... endif;` в альтернативном
   синтаксисе.

## 4. Схема БД — текущее состояние

Таблицы: `users`, `clients` (+`source` ENUM), `repairs` (+`order_type`
ENUM: repair/pc_build/account_memo; +поля квитанции — см. ниже),
`repair_parts` (+`cost` для расчёта прибыли), `parts_catalog`,
`repair_status_log`, `sms_log`, `expenses`.

`repairs.order_type` — дискриминатор, который объединяет ремонты,
сборки ПК и памятки по аккаунту в один список «Заказы».

## 5. Модули — статус

Готово и в проде (с оговоркой про миграции выше):
- Авторизация (bcrypt, сессии), `setup.php` — одноразовое создание админа.
- Клиенты (+ источник: авито/яндекс/2гис/google карты/сарафан/с улицы).
- Заказы (общий список, 3 способа создания — см. ниже), статусы,
  история статусов, **SMS через SMS.ru** (код готов в `src/sms.php`,
  дешёвая схема без своего имени отправителя — от 25 коп/SMS, от 7 коп
  при расходе >5000₽/мес; включается прописыванием `api_key` — реального
  `api_id` из личного кабинета sms.ru — в `config/config.php` на сервере,
  `provider => 'smsru'` уже поддержан кодом). Без `api_key` в конфиге —
  ведёт себя как раньше: логирует в `sms_log` со статусом `not_configured`,
  ничего не отправляет. Шаблон текста по умолчанию (`default_sms_message()`
  в `functions.php`): для статуса «готов» — «Здравствуйте! Вас приветствует
  сервис АВИОР. Устройство готово. С вас NNN ₽.» (сумма — комплектующие+
  услуги минус уже внесённая предоплата), для остальных статусов —
  прежний нейтральный текст «Заказ NN: статус — ...». Сотрудник видит
  готовый текст в форме и может отредактировать перед отправкой.
- Сборка ПК (`pc_build_new.php`) — создаёт заказ `order_type=pc_build`.
- Памятка по аккаунту (`account_memo_new.php`) — Apple ID/Google.
  **Пароли, секретные вопросы, 2FA-код НЕ сохраняются в БД** — только
  на распечатанном листе сразу после заполнения (сознательное решение
  по безопасности, Вейс уведомлён).
- Квитанция о приёмке (`repair_receipt.php`) — печать в 2 экземплярах
  (клиенту/сервису), 6 пунктов гарантийных условий по шаблону Вейса.
  В отличие от памятки — данные (серийный номер, комплектация, внешний
  вид, предоплата, срок, примечание, ФИО мастера) **сохраняются** в
  `repairs`, можно распечатать повторно без повторного ввода.
  Ставка ответственного хранения (₽/сутки) оставлена пустой строкой
  для заполнения от руки — как в оригинальном шаблоне.
  Стиль печатной формы переверстан под образец из реального экспорта
  ЛайвСклад (`Заказы.pdf`, загружен Вейсом): чёрный текст на белом,
  Arial/Helvetica, поля списком «жирная подпись: значение» без таблиц
  и цветных акцентов.
  На каждой квитанции — QR-код (через api.qrserver.com, `<img>`,
  без сервисной зависимости), ссылающийся на публичную страницу
  `public/order_status.php?order_no=...&phone=...` с текущим статусом
  заказа. При наведении на QR в браузере — тултip с текущим статусом
  (`title=`). **Важно:** QR рисуется, только если в `config/config.php`
  задан реальный `site_url` (не `https://example.ru` из примера) — иначе
  ссылку строить не от чего, и блок с QR просто не выводится. Рабочий
  домен подтверждён (§2) — на сервере в `config/config.php` должно быть
  `'site_url' => 'https://cms.avior.moscow',`.
- **Акт сдачи-приёмки выполненных работ** (`repair_act.php`) — формируется
  прямо из позиций заказа (`repair_parts`), отдельной формы ввода нет.
  Стиль и текст — по образцу, который прислал Вейс (`акт.pdf`): таблица
  позиций с колонкой «Гар-тия» (гарантия по каждой позиции — см. ниже),
  «Сумма чека/Скидка/Итого», сумма прописью (`money_in_words_rub()` в
  `functions.php` — собственная реализация числа-прописью на русском,
  проверена на кратные тесты), текст вердикта «...выполнены полностью и
  в срок...» — дословно из образца. В отличие от квитанции — 1 экземпляр
  на листе (в образце Вейса тоже один, не два).
- **Гарантия по позиции заказа** — поле `repair_parts.warranty`,
  выставляется прямо в форме добавления комплектующего/услуги на
  `repair_view.php` («нет» по умолчанию, если не заполнено — так и в
  образце ЛайвСклад). Показывается и в таблице позиций на экране, и в
  колонке «Гар-тия» акта.
- **Единая кнопка печатных документов** — на `repair_view.php` и в списке
  `repairs.php` вместо отдельных кнопок теперь выпадающий список
  (`<select>`) «📄 Печатные документы...» → Квитанция о приёмке / Акт
  выполненных работ. Простое решение вместо кастомного JS-меню — работает
  без доп. кода.
- **Отправка документов клиенту (WhatsApp/Telegram/Email)** — на страницах
  квитанции и акта (не на самих публичных ссылках) — кнопки, открывающие
  `wa.me/...` (номер клиента нормализуется 8→7), `t.me/share/url?...` и
  `mailto:...` с текстом и ссылкой на публичный просмотр документа.
  **Это не реальная серверная отправка** (нет SMTP/мессенджер-API на
  сервере) — кнопки открывают собственный WhatsApp/Telegram/почтовый клиент
  сотрудника с уже готовым текстом, отправляет он сам нажатием одной
  кнопки — тот же паттерн, что и кнопка «Поделиться» в самой первой смете
  (`smeta-sborka-pk.html`). Публичные ссылки, на которые ведут эти кнопки:
  `public/receipt_public.php` и `public/act_public.php` — без входа в CMS,
  доступ по `order_no+phone` (как и `order_status.php`). Требуют настоящего
  `site_url` в конфиге (см. выше) — без него кнопки отправки не появятся.
  Общий код вёрстки квитанции/акта вынесен в `src/print_templates.php`
  (`render_receipt_page()`, `render_act_page()`, `render_print_document_shell()`)
  — единая точка правды для стиля, используется и в CMS, и в публичных
  ссылках (параметр `$publicMode` убирает кнопки редактирования/отправки
  на публичной версии).
- **Публичные ссылки по токену** (`repairs.public_token`, VARCHAR(64)
  UNIQUE) — основной способ адресации `receipt_public.php`/`act_public.php`
  теперь `?id=6&token=...` вместо `?order_no=...&phone=...` (старый способ
  оставлен как fallback — оба работают одновременно). Токен генерируется
  один раз функцией `generate_public_token()` (`bin2hex(random_bytes(32))`,
  `functions.php`) при создании заказа во всех 4 точках создания
  (`repair_new.php`, `pc_build_new.php`, `account_memo_new.php`,
  `api/mobile/orders.php` POST). У заказов, созданных до миграции
  `2026_08_15_public_token.sql`, токен бэкафиллится SQL-функцией `SHA2()`.
  Мобильный API (`orders.php` GET) отдаёт `receipt_url`/`report_url` уже
  на основе токена, плюс сырое поле `public_token` в ответе. Плюс схемы:
  ссылка больше не содержит телефон клиента и её нельзя подобрать
  перебором номера заказа (в отличие от `order_no`, который просто
  инкрементится).
- Финансы (`finance.php`) — период (месяц/прошлый месяц/год/всё время),
  выручка/себестоимость/расходы/чистая прибыль, ручной учёт расходов.
- Аналитика (`analytics.php`) — источники клиентов, что чаще несут в
  ремонт, прибыльность по типу устройства (нужна заполненная
  себестоимость в позициях заказа, иначе прибыль = выручке).
- **Профиль** (`profile.php`) — смена своего пароля (с проверкой текущего)
  и отображаемого имени, доступно любому авторизованному сотруднику.
  Ссылка — по имени пользователя в правом верхнем углу шапки.
- **Сотрудники** (`employees.php`, только роль `admin`) — список учётных
  записей, добавление нового сотрудника (логин/имя/пароль/роль), смена
  роли (`admin`/`manager`) через select прямо в таблице, сброс пароля
  сотруднику (через `<details>` — раскрывающаяся мини-форма в строке),
  удаление сотрудника. Защита: нельзя удалить/понизить себя самого нельзя
  удалить, нельзя удалить или понизить **последнего** администратора
  (проверка `admin_count()`). Доступ ограничен через `require_admin()` в
  `src/auth.php` (`is_admin()` проверяет `current_user()['role']`). Ссылка
  в навигации и плитка на панели видны только администраторам.
- **Удаление заказа** (только роль `admin`) — кнопка «🗑 Удалить заказ» на
  `repair_view.php` (в шапке) и в списке `repairs.php` (иконка 🗑 в строке).
  POST `action=delete_repair`, проверка `require_admin()` внутри обработчика
  (не заглушка в шаблоне — реальная проверка на бэкенде, кнопка просто
  скрыта в UI для не-admin). Подтверждение через `confirm()` в браузере.
  `DELETE FROM repairs` — `repair_parts`/`repair_status_log` удаляются
  каскадом (FK `ON DELETE CASCADE`), `sms_log.repair_id` обнуляется
  (FK `ON DELETE SET NULL`), запись SMS-истории не теряется.
- Публичный API статуса заказа (`public/api/status.php`).
- **Мобильный API** (`public/api/mobile/*.php`) — для Android-приложения
  (Вейс собирает его сам через Gemini в Android Studio). Токен-аутентификация
  (таблица `api_tokens`, endpoint `auth.php`/`logout.php`), справочники
  (`meta.php`), клиенты (`clients.php` — список/поиск/создание), заказы
  (`orders.php` — список с фильтрами/деталь с позициями и историей/создание
  ремонта), смена статуса (`update_status.php`). Полная спецификация +
  готовый Kotlin/Retrofit-каркас для вставки в Android Studio — в
  `docs/MOBILE_API.md`. Через API пока создаются только заказы типа
  `repair` (не `pc_build`/`account_memo`).
- Автономная офлайн-версия формы сметы (`public/smeta-sborka-pk.html`,
  localStorage + Google Sheets через Apps Script) — легаси, работает
  без входа в CMS, но её заказы НЕ попадают в общий список «Заказы».
- **Подсказки автозаполнения** (`suggest_device_types()`, `suggest_device_models()`,
  `suggest_problem_descriptions()`, `suggest_part_names()` в `functions.php`) —
  для типа устройства/поломки/комплектующих: без отдельного справочника,
  строятся на лету из истории уже введённых значений
  (`GROUP BY ... ORDER BY COUNT(*) DESC`), топ по частоте использования.
  Модели устройств — **исключение**: `suggest_device_models()` объединяет
  историю заказов со справочником `device_model_catalog` (см. таблицу
  миграций выше, ⚠️ обязательна к применению) — реально чинившиеся модели
  всё равно наверху списка (частота), но подсказки работают сразу, даже
  без собственной истории. Каталог — не исчерпывающий список (это
  физически невозможно), а ~200 практических, часто встречающихся моделей;
  можно пополнять вручную через `INSERT INTO device_model_catalog (name) VALUES (...)`.
  Для `<input>` (тип/модель устройства, название комплектующего — includes
  parts_catalog) — нативный `<datalist>` (`render_datalist()`), браузер сам
  фильтрует по мере ввода. Для `<textarea>` (описание проблемы, т.к. datalist
  с textarea не работает) — кликабельные кнопки-чипы над полем
  (`render_suggestion_chips()`), клик подставляет готовый текст через
  `onclick` (JS-код экранируется `e()` перед вставкой в атрибут — не забыть
  этот паттерн при добавлении новых чипов). Подключено в `repair_new.php`
  (создание заказа) и `repair_view.php` (форма редактирования заказа +
  форма добавления комплектующего/услуги). В `pc_build_new.php` пока не
  подключено (другой домен — комментарий к сборке ПК, не тип/модель/поломка).
- **Визуальный пикер типа устройства** (`device_type_options()`,
  `render_device_type_picker()` в `functions.php`) — кликабельные карточки
  иконка+подпись над обычным текстовым полем `device_type` (сам input
  никуда не делся, остаётся источником истины и полем формы — пикер лишь
  подставляет в него значение через `selectDeviceType()`, общая JS-функция
  лежит в `src/layout_footer.php`, подключена везде). Пресеты: Настольный ПК,
  Моноблок, Ноутбук, Смартфон, Планшет, Игровая консоль, Аксессуары —
  плюс «Другое», при клике на которое поле очищается и открывается для
  ручного ввода (снимается `readonly`). При выборе пресета поле становится
  `readonly` (и на бэкенде ничего не меняется — как обычный текстовый ввод).
  В форме редактирования (`repair_view.php`) текущее значение заказа
  сравнивается со списком пресетов при загрузке страницы: если совпадает —
  соответствующая карточка сразу подсвечена и поле `readonly`; если это
  не пресет (старое произвольное значение) — выделено «Другое», поле
  редактируемое, как раньше. Подключено в `repair_new.php` и
  `repair_view.php` (форма редактирования). Список пресетов и иконки —
  через изменение `device_type_options()`, обновится сразу на обеих формах.

## 7. Как продолжить в новой сессии

1. Прочитать этот файл.
2. Если папка `outputs/cms-avior/` уже на месте (сохраняется между
   сессиями) — работать с ней напрямую.
3. Если папки нет (новая среда/новый компьютер) — клонировать репозиторий
   заново по ссылке из §2 (нужен свежий токен от Вейса, если старый не
   сохранён/отозван).
4. Перед пушем — прогнать проверки из §3.
5. После значимых изменений — обновить этот файл (модули/миграции/бэклог)
   и запушить вместе с кодом.
